# jest-polluter-finder

Give it a test file that fails only *after* other tests ran. It finds the **minimal set of test files** that cause the failure
(delta debugging / ddmin) and prints a one-line reproduction command.

```
$ npx jest-polluter --victim tests/vic_cwd.test.js
Victim: tests/vic_cwd.test.js
Minimal polluter set (1): tests/pol_cwd.test.js
Reproduced 5/5 confirmation runs
Repro: npx jest --runInBand --runTestsByPath tests/pol_cwd.test.js tests/vic_cwd.test.js
```

It states **what** reproduces and **how often** — never *why*. Try it on the bundled demo (see Scope):
`npm test` runs the finder against it.

## How it works
1. `jest --listTests` → candidate files. The victim must pass alone and fail after *all* candidates (else: no pollution / not pollution).
2. ddmin shrinks the candidate set. Each probe is `jest --runInBand --runTestsByPath <subset…> <victim>` with a custom
   sequencer that fixes the order; only the **victim's** result counts (a polluter failing itself is not reproduction).
3. The final set is re-run `--confirm` times (default 5); the `N of N` count is reported.

Flaky pollution: `--repeats K` treats a subset as failing if any of K tries fails. Extra jest args go after `--`.

## Scope
* File-level granularity, Jest only (Vitest: not yet). Test-level (`-t`) bisection: not yet.
* Jest sandboxes globals, `process.env` and the module registry per file, so cross-file pollution must travel through shared
  process state: core modules, `process.chdir`, files on disk, ports, real timers. The demo (`demo/`, generated by
  `node demo/gen.mjs`) has five such kinds: patched `os`, `process.chdir`, leftover file, patched `zlib`, patched `child_process`
  — plus 6 clean decoys. `npm test` checks the finder returns exactly the right polluter for each.
